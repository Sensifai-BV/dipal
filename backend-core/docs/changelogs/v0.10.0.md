# v0.10.0 — Consolidate Retry into Rerun Endpoint

## Summary

Removes the redundant `/retry/` endpoint that created new job records on each retry (breaking resume flows), and merges all retry validation logic into the existing `/rerun/` endpoint. The `/rerun/` endpoint now enforces status checks, `can_retry` flag, max-retries limit, and increments `retry_count` — all while preserving the original job ID.

## All Changes

### Breaking Changes

- `refactor(jobs)`: **Removed** `POST /api/jobs/{job_id}/retry/` endpoint entirely. All retry/rerun operations now go through `POST /api/jobs/{job_id}/rerun/`.
- `refactor(jobs)`: The `/rerun/` endpoint no longer accepts `reset_status` or `force_restart` query parameters. Use `resume=true` to resume from the failed stage, or omit it (default `resume=false`) to restart from the beginning.

### Features

- `feat(jobs)`: `/rerun/` now validates job status — only `failed` or `cancelled` jobs can be retried.
- `feat(jobs)`: `/rerun/` now checks `can_retry` flag — jobs marked as non-retryable are rejected with `400`.
- `feat(jobs)`: `/rerun/` now enforces `MAX_RETRIES = 3` — exceeding the limit returns `400` with a suggestion to check logs.
- `feat(jobs)`: `/rerun/` increments `job.retry_count` on every rerun and returns it in the response.
- `feat(jobs)`: `/rerun/` response now includes `retry_count`, `resume_from`, and `dataset` (id + name).
