# v0.10.19 — Camera XMP namespace fix, MRK tagged-token parser, gdalwarp nodata edge fix

## Summary

Three bugs diagnosed from production logs that caused irradiance values to be
silently discarded (striping / washed-out reflectance), RTK/PPK MRK positions to
be ignored entirely (falling back to ±1–3 m EXIF GPS), and vegetation index maps
to contain corrupted pixels at field boundaries.

---

## Bug Fixes

### fix(calibration): Camera XMP namespace URL was wrong — irradiance always fell back to 1.0

**Files:**
- `shared/band_detection/metadata_reader.py`
- `services/radiometric_calibration/app/core/services/mavic_m3m_calibration.py`

**Root cause**

`metadata_reader.py` mapped the `Camera:` XML namespace prefix to
`http://www.micasense.com/1.0/` (MicaSense).  DJI M3M images declare
`xmlns:Camera="http://pix4d.com/camera/1.0"` (Pix4D schema).  Because the URL
did not match, the ElementTree XML parser could not resolve any `Camera:*`
attribute, making the following fields invisible to the XML path:

- `Camera:Irradiance` → irradiance defaulted silently to `1.0`
- `Camera:BlackCurrent` → black level fell back to hardcoded 3200
- `Camera:IrradianceExposureTime`, `Camera:IrradianceGain`, `Camera:SunSensor`
  → all lost

The regex fallback in `_parse_xmp_regex_fallback` does catch `Camera:Irradiance`
correctly, but only when the XML path fails entirely — a race condition based on
token order in the XMP block.  The correct fix is to use the right namespace URL.

`mavic_m3m_calibration.py` also looked up `BlackLevel` in the metadata dict when
the actual DJI XMP key is `Camera:BlackCurrent` (Pix4D schema), so the black
level correction was never applied and defaulted to 3200 unconditionally.

**Fix**

- `_NS_PREFIXES["Camera"]` changed from `http://www.micasense.com/1.0/` to
  `http://pix4d.com/camera/1.0`.
- `MICASENSE_NS` constant retained for reference; MicaSense sensors are still
  supported via the existing regex fallback (`Camera:Irradiance` pattern).
- Added `BlackCurrent`, `SunSensor`, `IrradianceExposureTime`, `IrradianceGain`
  to `MICASENSE_XMP_PROPERTIES` so the regex fallback also catches these.
- `mavic_m3m_calibration.py` `black_level` extraction changed to:
  `raw.get("BlackLevel") or raw.get("BlackCurrent", 3200.0)` — handles both the
  old key (in case other firmware writes it) and the correct Pix4D key.

**Impact**

Before this fix every DJI M3M image had `irradiance=1.0` regardless of DLS
output.  Reflectance values were therefore not normalised for sun angle, causing
systematic strip-to-strip offsets (the "striping" artefact) and an overall
washed-out appearance in vegetation index maps.

### fix(sfm): MRK parser failed on tagged-token coordinate format — RTK positions silently discarded

**File:** `services/sfm/app/core/services/colmap_service.py`

**Root cause**

`_parse_mrk_file` assumed the DJI MRK file used plain space-separated floats for
latitude, longitude and altitude.  The actual DJI M3M RTK MRK format uses
comma-tagged tokens:

```
1  454400.746373  [2323]  -40,N  -15,E  83,V  41.13015180,Lat  23.42749964,Lon  94.597,Ellh  ...
```

`float("41.13015180,Lat")` raises `ValueError`, so the `except ValueError:
continue` handler silently skipped every line.  `_parse_mrk_file` returned an
empty dict, `geo_register()` logged `"MRK file found but could not be parsed —
falling back to EXIF GPS"`, and all RTK positions were discarded.

**Fix**

The primary parsing path now uses three compiled regexes to extract the
tagged-token coordinates regardless of column position:

```python
_LAT_RE  = re.compile(r"([\d.]+),Lat")
_LON_RE  = re.compile(r"([\d.]+),Lon")
_ELLH_RE = re.compile(r"([\d.]+),Ellh")
```

The original column-offset logic is retained as a fallback for older DJI
firmware that writes plain floats.

**Impact**

`geo_register()` now receives ±1–3 cm RTK positions instead of ±1–3 m EXIF GPS.
This reduces geo-registration error from ~0.37 m to ~3 cm for datasets captured
with RTK lock, improving ortho/DSM absolute accuracy and reducing the residuals
seen in `model_aligner` alignment diagnostics.

### fix(orthomosaic): gdalwarp bilinear resampling blended nodata at footprint edges — corrupted NDVI boundaries

**File:** `services/orthomosaic_generation/app/core/algorithms/ms_orthorectification.py`

**Root cause**

`gdalwarp` was called with `-r bilinear` but without `-wo UNIFIED_SRC_NODATA=YES`.
GDAL's bilinear resampler, when computing output pixels near a valid/nodata
boundary, averages the neighbouring input pixels including any that have the
`-srcnodata` sentinel value (`-9999`).  The arithmetic average of a valid
reflectance value (e.g. `0.3`) and the nodata sentinel (`-9999`) produces a large
negative value (e.g. `-1000`) that:

1. Passes the `(data != _NODATA) & np.isfinite(data)` validity test in Pass 1
   (the value is not exactly `-9999` and is finite).
2. Gets included in the feather-blend weighted sum.
3. Passes through to `vegetation_indices.py` which also only excludes exact
   `-9999` values.
4. Produces a ring of large-negative NDVI/NDRE/GNDVI values at every image
   footprint boundary inside the field.

**Fix**

Added `-wo UNIFIED_SRC_NODATA=YES` to the `gdalwarp` command.  This flag
instructs GDAL to treat any output pixel whose bilinear kernel overlaps even one
nodata source pixel as nodata itself, preventing blended sentinel values from
entering the composite.

**Impact**

Field-boundary corruption rings in NDVI/NDRE/GNDVI maps are eliminated.  The
tradeoff is a 1–2 pixel erosion of valid data at each image footprint edge, which
is already partially handled by `_DSM_MASK_EROSION_PX = 15` and
`_edge_distance_weight()` feathering.
