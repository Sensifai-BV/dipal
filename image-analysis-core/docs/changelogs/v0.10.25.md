# v0.10.25 — Multispectral orthorectification through SFM poses (NDVI "puzzle-pieces" fix)

## Summary

Multispectral index maps (NDVI/NDRE/GNDVI) rendered as a "puzzle whose pieces are
placed in the wrong locations": each band tile was direct-georeferenced from raw EXIF
GPS, scaled by a guessed above-ground altitude, and rotated by yaw only (nadir
assumption, roll/pitch ignored). Because every tile was placed independently with no
tie-points, GPS scatter (1–3 m) plus ignored tilt and scale error did not cancel
between images — unlike the RGB orthomosaic and DSM, which are rasterized from the one
globally-consistent SFM dense point cloud. This release adds a pose-driven band
orthorectification path (`pose_ortho.py`) that projects **every DSM cell through the
co-acquired RGB image's SFM pose and FULL_OPENCV intrinsics**, maps the resulting RGB
pixel into each band's sensor frame using the DJI manufacturer geometry
(`DewarpHMatrix`⁻¹ + `RelativeOpticalCenter`), and bilinearly samples the calibrated
reflectance — so all bands co-register by construction against the same surface that
produced the RGB ortho. The path is opt-in via `ORTHO_USE_POSE_ORTHO=true` and falls
back to the GPS path when the SFM artifacts or band manifest are unavailable.

It also fixes a grouping bug that made the pose path **silently fall back to GPS on
every production run**: calibrated reflectance filenames carry a `_reflectance` suffix
(`DJI_..._MS_G_reflectance.tif`) that the raw-keyed manifest map
(`DJI_..._MS_G`) lacks, so the stem lookup matched nothing → 0 captures grouped → GPS
fallback → the same flight-line strips. On the run_3rd_13_jun dataset (119 M3M
captures) the fix takes grouped captures from 0 → 119, band coverage from 47.6 %
(GPS strips) → 70.3 %, and turns the strip-mosaic NDVI into one coherent field.

Two blend artefacts surfaced once the pose path engaged and are also fixed here: the
original radial nadir weight left **circular "scallop" seams** (each cell dominated by
one capture's circular disk, re-lighting its centre-bright vignette), and bands were
painted over the **filled** DSM so they **spilled past the RGB orthomosaic boundary**.
The blend is now a band-coherent rectangular edge-feather (uniform across each
footprint interior, feathering only the outer 30 %), and bands are clipped to the
unfilled point-cloud coverage. On run_13_jun_4th this cut NIR/NDVI high-frequency seam
energy ~35 % and brought band coverage to 55.7 % of the grid, matching the 55.9 % RGB
ortho.

## Bug Fixes

### fix(orthomosaic): match calibrated `_reflectance` stems to raw manifest entries in pose grouping

**File:** `services/orthomosaic_generation/app/core/algorithms/pose_ortho.py`

**Root cause**

`_group_captures_by_band` looked up each reflectance image's original raw path with
`original_map.get(refl.stem)`. The calibrated reflectance stem
(`DJI_20240719091917_0100_MS_G_reflectance`) carries a `_reflectance` suffix that the
manifest map — keyed by the raw filename stem (`DJI_20240719091917_0100_MS_G`) — does
not. Every lookup returned `None`, so no captures were grouped, and
`orthorectify_bands_pose` returned `None` and fell back to the GPS-guided path. The
fallback was logged at WARNING but otherwise silent, so a full pipeline run with
`ORTHO_USE_POSE_ORTHO=true` still produced GPS strip-mosaics.

**Fix**

- Strip the `_reflectance` suffix from the reflectance stem before the lookup
  (`refl.stem.removesuffix("_reflectance")`).
- Add a capture-sequence fallback: index the manifest's raw paths by their 4-digit
  capture sequence and match on that when the stem lookup misses, so future calibrated-
  vs-raw naming drift cannot silently disable the pose path.
- Make the fallback diagnosable: when 0 captures group, the WARNING now reports the
  reflectance-tif count, manifest-entry count, and pose count so the cause is visible
  in logs rather than costing a full pipeline run.

**Validated result (run_3rd_13_jun, 119-capture M3M dataset)**

| Metric | Before (GPS fallback) | After (pose-ortho) |
|---|---|---|
| Captures grouped from manifest | 0 | 119 |
| Captures with a valid footprint | — | 119 / 119 |
| Band coverage of DSM extent | 47.6 % (strips) | 70.3 % |
| NDVI mean (vegetated field) | — | 0.384 |
| Visual | diagonal flight-line strips + gaps | one coherent field |

## Features

### feat(orthomosaic): pose-driven multispectral orthorectification through SFM (`ORTHO_USE_POSE_ORTHO`)

**Files:** `services/orthomosaic_generation/app/core/algorithms/pose_ortho.py` (new),
`services/orthomosaic_generation/app/core/algorithms/ms_orthorectification.py`

- New module `pose_ortho.py`:
  - `load_sfm_geometry` reads `sparse/0/{cameras,images}.bin`, the Sim3 in
    `geo_transform.txt` (`scale qw qx qy qz tx ty tz`), and `geo_reference.json`
    (UTM EPSG); returns `None` for a safe GPS fallback when any artifact is missing.
  - `orthorectify_bands_pose` precomputes the local-SFM coordinate of every valid DSM
    cell (UTM → ECEF → Sim3⁻¹ → local), then for each capture projects through the RGB
    pose + FULL_OPENCV intrinsics, maps RGB→band via `DewarpHMatrix`⁻¹ and
    `−RelativeOpticalCenter`, and bilinearly samples the calibrated reflectance, writing
    each band to `{band}_ortho.tif` on the DSM grid.
  - **Blend = band-coherent rectangular edge-feather.** The per-capture, per-cell weight
    is `clip(edge / _FEATHER_FRAC, 0, 1)` where `edge` is the normalised distance of the
    projected point to the nearest RGB image border (uniform 1 across the footprint
    interior, ramping to 0 only in the outer 30 %). Iso-weight contours follow the
    rectangular sensor footprint, so overlapping captures cross-fade only at their seams
    and average equally elsewhere — this removes the circular "scallop" seams a radial
    weight produced and averages out each capture's centre-bright vignette/BRDF texture.
    The single weight is shared across all bands so they stay co-registered. (On
    run_13_jun_4th this cut NIR high-frequency seam energy ~35 % and NDVI ~36 % vs the
    earlier radial weight.)
  - **Boundary clipped to the real cloud.** Bands are painted only over the unfilled
    `dsm.tif` coverage (read via `_real_coverage_mask`, trimmed by `_erode_mask`, a
    scipy-free 4-connected binary erosion), not the filled DSM. This stops multispectral
    data from spilling into the filled-DSM margin beyond the RGB orthomosaic boundary
    (run_13_jun_4th: band coverage 72.8 % of grid → 55.7 %, matching the 55.9 % RGB
    ortho).
- `ms_orthorectification.orthorectify_bands` calls the pose path first when
  `ORTHO_USE_POSE_ORTHO=true` and a band manifest is present, falling back to the GPS
  path when it returns `None`. `_read_dsm_metadata` now also returns the DSM `path`.
- 22 unit tests in `tests/unit/test_pose_ortho.py` (capture-sequence parsing,
  quaternion→rotation, FULL_OPENCV projection, bilinear sampling, DewarpHMatrix /
  RelativeOpticalCenter parsing, the reflectance-stem grouping regression, and the
  binary-erosion helper).

> **Operator note:** enable both `ORTHO_USE_POSE_ORTHO=true` (this feature) and
> `COLMAP_SEED_FACTORY_INTRINSICS=true` (v0.10.24) together — the pose projection
> samples the RGB intrinsics and DSM produced by the seeded reconstruction; with seeding
> off the focal drifts and the DSM domes, corrupting the projection geometry.

## Infrastructure

### infra(orthomosaic): add `scipy==1.13.1` to the orthomosaic image

The DSM coverage-mask erosion in `ms_orthorectification._read_dsm_metadata` imports
`scipy.ndimage.binary_erosion`, but `scipy` was never in
`services/orthomosaic_generation/requirements.txt`, so the container logged
*"scipy not available — DSM coverage mask erosion skipped"* and the noisy point-cloud
perimeter leaked into outputs. Pinned `scipy==1.13.1` (compatible with the image's
`numpy==1.26.0` — `numpy<2.3,>=1.22.4` — and Python 3.12). The new pose path does not
depend on it (it ships its own scipy-free `_erode_mask`), but the GPS path and the DSM
mask erosion now work as intended.

### infra(sfm): build GDAL + PDAL from source in the SFM image

`colmap_service._write_utm_pointcloud` shells out to `pdal pipeline` to reproject the
ECEF dense cloud to UTM and write `fused_utm.ply`, but the SFM Dockerfile installed no
PDAL, so the step failed (non-fatally) with *"Command not found: pdal"* and only the
ECEF `fused_georef.ply` was produced. **PDAL is not packaged for Ubuntu 24.04 (noble)** —
it never migrated into the release (`apt-cache search pdal` is empty even with `universe`
enabled) — and PDAL requires GDAL, so both are now built from source (GDAL v3.12.2 then
PDAL 2.9.2) into an isolated `/deps-install` prefix in the multi-stage builder and copied
into the runtime stage, mirroring `services/orthomosaic_generation/Dockerfile`. The
runtime stage gains the required shared libs (`libproj25`, `proj-data` for `proj.db`,
`libgeotiff5`, `liblaszip8`, `libtiff6`, `libjpeg-turbo8`, `libpng16-16t64`, `libexpat1`,
`libsqlite3-0`, `libxml2`, `libzstd1`) plus `ldconfig`. SFM uses PDAL only as a CLI — it
imports no Python GDAL/osr.

## Breaking Changes

No changes. The pose path is opt-in (`ORTHO_USE_POSE_ORTHO` default `false`) and falls
back to the existing GPS path when disabled or when SFM/manifest artifacts are absent;
deployments that do not set the flag behave identically to v0.10.24.
