# v0.10.18 — Multispectral alignment hard error, GPS prior fix, NDVI pipeline fix, irradiance warning

## Summary of issues fixed (tester report — May 2026)

The tester reported two problems after v0.10.17:

1. Multispectral band orthos were visually misaligned (images offset / rotated
   relative to the RGB orthomosaic).
2. Coordinates could not be extracted from the 3D point cloud.

Additionally, a structural code defect in `mavic_m3m_calibration.py` caused
vegetation indices to be computed from uncorrected DN values instead of
calibrated reflectance, and the Irradiance fallback was completely silent.

---

## Fix 1 — Multispectral misalignment: hard error on missing `band_manifest`
**File:** `services/orthomosaic_generation/app/core/algorithms/ms_orthorectification.py`

### Root cause

`orthorectify_bands` previously fell back silently to `_median_composite_band`
when `band_manifest` contained no original image paths for a band.
`_median_composite_band` resizes all images to DSM pixel dimensions with no
geographic positioning — producing the rotated / offset mosaic visible in the
tester's image.  The fallback was designed as a legacy escape hatch but was
triggering silently in production.

### Fix

The silent warning + fallback is replaced with a `RuntimeError`:

```python
raise RuntimeError(
    f"band_manifest missing original image paths for band '{band_name}'. "
    "GPS-guided warping is required for correct multispectral alignment. "
    "Ensure band_manifest is populated with source image file paths before "
    "calling orthorectify_bands."
)
```

This surfaces the root cause immediately rather than producing a geometrically
incorrect output that looks plausible but is wrong.

## Fix 2 — 3D point cloud in local SFM space: GPS priors not used by glomap
**File:** `services/sfm/app/core/services/colmap_service.py`

### Root cause — default mismatch

`ColmapSettings.mapper_use_prior_position` defaulted to `False`.  The `.env`
file sets `COLMAP_MAPPER_USE_PRIOR_POSITION=1`, so the setting was correctly
overridden at runtime for the production deployment.  However the default value
was wrong, meaning any environment without the `.env` override (CI, local dev,
new deployments) would run glomap without GPS priors.  Without GPS priors,
glomap produces a reconstruction in arbitrary local space which
`model_aligner` must then align; for agricultural surveys with repeating
texture (crop rows) this alignment is unreliable.

### Root cause — glomap command never passed the flag, and wrong flag names used

The installed glomap version does **not** have `--GlobalPositioning.use_prior_position`
or `--GlobalPositioning.prior_position_loss_scale`.  GPS priors in this version
are controlled by the top-level `--constraint_type` flag:

```
ONLY_POINTS               visual-only reconstruction (glomap default)
ONLY_CAMERAS              GPS-only constraints
POINTS_AND_CAMERAS_BALANCED   balanced visual + GPS
POINTS_AND_CAMERAS        visual + GPS, full weight
```

**Important:** `POINTS_AND_CAMERAS_BALANCED` and `POINTS_AND_CAMERAS` require
that the COLMAP database's `prior_t` values are in a metric coordinate system
(ECEF or local XYZ).  `pycolmap.import_images` populates `prior_t` from GPS
EXIF as `[lat, lon, alt]` in degrees/metres — not a metric coordinate system.
Passing this to glomap's global positioning makes the camera constraints
geometrically degenerate, causing glomap to triangulate **0 3D points**.  With
0 points the co-visibility graph is empty and `image_undistorter` writes a
`stereo.txt` with no source images for any reference image, causing
`patch_match_stereo` to ignore all images.

GPS alignment is already handled correctly by the existing `geo_register()` →
`colmap model_aligner` step **after** reconstruction.  Glomap must run in
visual-only mode (`ONLY_POINTS`) so it stays in local SFM space; `model_aligner`
then aligns the model to GPS using `ref_images.txt`.

### Fix

1. Changed default: `mapper_use_prior_position: bool = True`
2. Added `glomap_constraint_type: str = "ONLY_POINTS"` setting (explicit, no magic
   `auto` sentinel).  Set `COLMAP_GLOMAP_CONSTRAINT_TYPE=ONLY_POINTS` in env.
3. Glomap command appends `--constraint_type ONLY_POINTS` (visual-only, safe).
4. `.env` and `.env.example` updated with corrected documentation.

Note: `fused.ply` is always in local SFM coordinates.  The georeferenced output
is `fused_georef.ply` (produced by `mesh()` via `model_transformer` +
`geo_transform.txt`).  Instruct testers to open `fused_georef.ply` for
coordinate extraction.

## Fix 2b — PPK/RTK upgrade for `geo_register()` using DJI `.MRK` file
**File:** `services/sfm/app/core/services/colmap_service.py`

### Context

Standard GPS stored in image EXIF has ±1–3 m horizontal accuracy.  DJI M3M
drones equipped with RTK/PPK modules record a ``Timestamp.MRK`` file that maps
each image capture event to a high-accuracy position (±1–3 cm).  This data was
not previously used by the pipeline — `geo_register()` was using EXIF GPS only.

### Fix

Added two new module-level helpers:

**`_parse_mrk_file(mrk_path)`** — parses the DJI ``.MRK`` format (tab/space
separated, ``<index> <date> <time> <lat> <lon> <alt> [fix_type …]``).  Handles
both split date/time tokens and combined ISO-8601 datetime tokens.  Returns a
mapping of zero-padded 4-digit image index → ``(lat, lon, alt_m)``.

**`_upgrade_gps_with_ppk(exif_entries, mrk_gps)`** — merges PPK positions into
the EXIF GPS list.  Matches by extracting the 4-digit sequence number from DJI
filenames (``DJI_YYYYMMDDHHMMSS_NNNN_X.JPG`` → ``NNNN``).

`geo_register()` now:
1. Searches for ``*.MRK`` files in the workspace root and subdirectories.
2. If found, calls both helpers and logs how many images were upgraded.
3. Falls back to EXIF GPS for any images not covered by the MRK file.

The net effect is that `colmap model_aligner` receives centimetre-accurate
reference positions instead of metre-accurate EXIF GPS, producing a tighter
geo-referenced model.

## Fix 3 — NDVI from uncorrected DN: add `calculate_vegetation_indices_from_paths`
**File:** `services/radiometric_calibration/app/core/algorithms/vegetation_indices_calculation.py`

### Root cause

`VegetationIndicesCalculator.calculate_vegetation_indices(red_band, nir_band)`
accepted raw numpy arrays and applied only a plain normalised-difference
formula — bypassing the full radiometric correction chain (vignetting
correction → distortion correction → homography alignment → camera-signal
normalisation → irradiance-based reflectance conversion).  NDVI computed from
uncorrected DN values is not agronomically meaningful and varies with exposure
settings, not just canopy properties.

### Fix

Added `calculate_vegetation_indices_from_paths(red_path, nir_path)` which:
1. Loads each band via `drone_image_processor.load_image()` (applies all
   correction steps and builds `CalibrationMetadata`).
2. Calls `drone_image_processor.calculate_ndvi()` which uses
   `_ensure_reflectance()` → `calculate_reflectance()` → reflectance conversion
   with irradiance normalisation.

The existing `calculate_vegetation_indices(red_band, nir_band)` is kept for
callers that already supply calibrated reflectance arrays, with its docstring
clarified to document this precondition.

## Fix 4 — Silent irradiance fallback and dead code in `mavic_m3m_calibration.py`
**File:** `services/radiometric_calibration/app/core/services/mavic_m3m_calibration.py`

### Root cause — dead code

`get_corrected_image` and `calculate_other_indices` were indented as nested
functions inside `_safe_float`, making them unreachable dead code (Python never
executes them because `_safe_float` always returns before reaching the `def`
statements).  `calculate_other_indices` additionally called
`self.calculate_camera_signal(band_name)` (raw DN normalisation) instead of
`self._ensure_reflectance(band_name)` (calibrated reflectance), so any code
that somehow invoked it would have produced wrong index values.  Both methods
are already correctly implemented on `BaseDroneCalibrator` via inheritance.

### Root cause — silent irradiance default

`irradiance=float(raw.get("Irradiance", 1.0))` silently defaulted to `1.0`
with no log message.  This caused radiometric striping: each image had the same
nominal irradiance regardless of actual sun angle, so inter-strip illumination
differences appeared as reflectance offsets.

### Fix

1. Removed the dead `get_corrected_image` / `calculate_other_indices` methods
   from inside `_safe_float`.
2. Extracted irradiance parsing into `_extract_irradiance(raw, image_path)`
   which logs a `WARNING` when the field is absent, directing the operator to
   verify DLS sensor activation and XMP namespace parsing.
3. Removed the now-unused `import numpy as np` from module scope.
