# v0.10.12 — Geo-Registration & Stereo Fusion: Apply Changelog-Documented Fixes That Were Never Committed

**Date:** 2026-05-11

Four bugs that were described in v0.10.9, v0.10.10, and v0.10.11 changelogs but whose
fixes were never committed to the codebase.  The running containers continued to use
the broken code, causing every geo-registration attempt to fail and every
`stereo_fusion` run to produce 0 fused points.  This release applies the real fixes.

---

## Bug Fixes

### 1. `geo_register`: `--ref_images_path` passed image directory instead of GPS text file

**File:** `services/sfm/app/core/services/colmap_service.py`

`colmap model_aligner --ref_images_path` expects a plain-text file where each line is:

```
image_filename.jpg  <latitude>  <longitude>  <altitude_m>
```

The previous code passed `str(image_path)` (the image directory).  COLMAP attempted
to read GPS positions from a file listing, found nothing parseable, and exited with
return code 1.  The `ref_images_txt` variable was declared but never written or used.

**Fix:** write `ref_images.txt` from the GPS entries extracted by
`_extract_gps_from_images()` and pass its path to `--ref_images_path`.  Column order
is `lat lon alt` (ENU / COLMAP GPS convention).

---

### 2. `geo_register`: `--alignment_type gps` and `--robust_alignment` flags not supported by COLMAP 3.13.0

**File:** `services/sfm/app/core/services/colmap_service.py`

The `colmap model_aligner` invocation used flags that do not exist in COLMAP 3.13.0
(commit `0b31f981`, 2025-11-07):

```
Failed to parse options - unrecognised option '--robust_alignment'.
```

The v0.10.9 changelog claimed these were removed and v0.10.10 claimed `--alignment_max_error`
was added, but neither change was committed.

**Fix:** replaced the entire flag set with the correct COLMAP 3.13.0 API:

| Old (invalid) | New (COLMAP 3.13.0) |
|---|---|
| `--alignment_type gps` | `--alignment_type ecef` |
| `--robust_alignment 1` | *(removed)* |
| `--robust_alignment_max_error <x>` | `--alignment_max_error <x>` |
| `--ref_images_path <dir>` | `--ref_images_path <text_file>` |
| *(missing)* | `--ref_is_gps 1` |

`ecef` is used (not `enu`) because downstream PDAL pipelines and `geo_reference.json`
assume `input_srs: "EPSG:4978"` (ECEF).  Using `enu` would produce a local-frame
point cloud that breaks the ECEF→UTM reprojection in `orthomosaic_service.py`.

---

### 3. `stereo_fusion`: `fusion_max_depth_error = 0.01` rejected all pixels after ECEF alignment

**Files:** `services/sfm/app/core/services/colmap_service.py`, `.env`, `.env.example`

v0.10.11 documented this fix but did not commit it.  With `max_depth_error = 0.01`
(1 %), two depth estimates for the same pixel must agree within 1 % of the depth
value.  After geo-registration in ECEF coordinates the typical alignment residual
is ~1 m at ~10 m flight altitude — a 10 % relative error — so `stereo_fusion`
rejected every pixel and wrote `fused.ply` with 0 points.

COLMAP printed:
```
Could not fuse any points. This is likely caused by incorrect settings - 
filtering must be enabled for the last call to patch match stereo.
```

**Fix:** raised `fusion_max_depth_error` from `0.01` → `0.05` in:
- `ColmapSettings.fusion_max_depth_error` (default in code)
- `COLMAP_FUSION_MAX_DEPTH_ERROR` in `.env`
- `COLMAP_FUSION_MAX_DEPTH_ERROR` in `.env.example`
