# v0.10.11 — SFM Geo-Registration Robustness + Dense Fusion Fix

**Date:** 2026-05-07

Five targeted fixes to the SFM geo-registration and dense-fusion pipeline.
The root symptom was `fused.ply` containing only ~64 points instead of millions.

---

## Bug Fixes

### 1. `stereo_fusion`: near-empty point cloud due to `max_depth_error` too tight

**File:** `services/sfm/app/core/services/colmap_service.py`  
**Setting:** `COLMAP_FUSION_MAX_DEPTH_ERROR` (`.env`, `.env.example`)

`StereoFusion.max_depth_error = 0.01` (1 %) means two depth estimates for the same
pixel must agree within 1 % of the depth value.  After geo-registration the typical
alignment residual is ~1 m at ~10 m flight altitude — a 10 % relative error — so
`stereo_fusion` rejected virtually every pixel.

**Fix:** default raised from `0.01` → `0.05` (5 %) in `ColmapSettings` and both env
files.

---

### 2. `geo_register`: sparse model overwritten in-place by `model_aligner`

**File:** `services/sfm/app/core/services/colmap_service.py`

Previously `--input_path` and `--output_path` pointed at the same `sparse/0`
directory.  If `model_aligner` produced a bad alignment transform the only copy of
the GLOMAP reconstruction was permanently corrupted with no way to recover without
re-running the full pipeline.

**Fix:** two-phase write:
1. `model_aligner` writes output to a fresh staging directory `sparse/0_aligned`.
2. On success: `sparse/0` is removed and `0_aligned` is renamed to `0` (single
   filesystem operation — effectively atomic).
3. On failure: `0_aligned` is removed; `sparse/0` is never touched.

A fallback guard handles the (extremely rare) case where `rmtree` succeeds but
`rename` fails — it restores `sparse/0` from `0_original` so downstream steps
(`undistort`, `compute_depthmaps`, `mesh`) can still run.

---

### 3. `geo_register`: no backup of pre-alignment sparse model

**File:** `services/sfm/app/core/services/colmap_service.py`

Before calling `model_aligner`, the GLOMAP reconstruction is now copied to
`sparse/0_original` (skipped if the backup already exists from a previous run).
This makes it possible to:
- Re-run geo-registration with different settings without re-running GLOMAP.
- Recover manually if alignment is bad (RMSE / scale warnings — see fix #4).

---

### 4. `geo_register`: no diagnostic for bad alignment transform

**File:** `services/sfm/app/core/services/colmap_service.py`

`model_aligner` prints the estimated similarity transform (including scale factor and
RMSE) to stdout, but nothing surfaced this in the logs.  A bad coordinate/unit
mismatch can produce a scale factor far from `1.0` or a huge RMSE, silently
corrupting the dense pipeline.

**Fix:** `_run_command` output is now scanned with two regexes:
- `Scale: <value>` — warns if deviation from `1.0` exceeds 10 %.
- `RMSE: <value>` — warns if RMSE exceeds `5 × geo_registration_max_error` metres.

Both warnings include the path to `sparse/0_original` for recovery.

---

### 5. `geo_register`: GLOMAP camera outlier filtering after alignment

**File:** `services/sfm/app/core/services/colmap_service.py`  
**Setting:** `COLMAP_GEO_REGISTRATION_OUTLIER_FILTER_M` (default `10.0` m)

New helper `_filter_misaligned_cameras()` (uses `pycolmap` API):
- Reads GPS entries from `ref_images.txt` and converts to ECEF via `_gps_to_ecef()`.
- Loads the aligned reconstruction and checks each registered camera's
  `projection_center()` against its GPS reference.
- Cameras whose ECEF position deviates by more than `geo_registration_outlier_filter_m`
  are deregistered and the model is re-saved.

GLOMAP occasionally places a small tail of cameras tens of metres away from their
true GPS position.  Those cameras produce incoherent depth maps that cause
`stereo_fusion` to discard almost all points even with the relaxed `max_depth_error`.

New setting `geo_registration_outlier_filter_m: float = 10.0` — set to `0` to
disable filtering.

## Pipeline Impact

All steps downstream of `geo_register` (`undistort`, `compute_depthmaps`, `mesh`,
`compute_statistics`, `export_report`) resolve the sparse model via
`_get_sparse_path(project_id) / "0"`.  After the atomic rename `0_aligned → 0` they
transparently use the aligned model — no changes required in any other step.

The `0_original` and `0_aligned` directories are written alongside `sparse/0` inside
the `run_path/sparse/` directory and are never referenced by any other pipeline step.
