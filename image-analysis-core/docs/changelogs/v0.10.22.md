# v0.10.22 — SFM camera-model doming fix + UTM point cloud for coordinate extraction

## Summary

Two SFM-stage fixes diagnosed directly from a production reconstruction. First,
the reconstruction was running with the **SIMPLE_RADIAL** camera model (a single
distortion coefficient) instead of the configured **OPENCV** model, because
`pycolmap.import_images` pre-creates the camera rows with its default model and
`feature_extractor`'s `--ImageReader.camera_model OPENCV` is then silently ignored.
A single-`k1` model cannot represent real drone-lens distortion, so bundle
adjustment bends the reconstruction into a bowl ("doming") — visible as a smooth
radial trend in the DSM and as multispectral band misalignment when bands are
warped onto the domed surface. The camera model is now pinned at import time and
verified by reading it back from the database. Second, testers could not extract
coordinates from the point cloud: `fused.ply` is in local SFM space and
`fused_georef.ply` is in ECEF (EPSG:4978) geocentric metres — both unusable for
reading easting/northing and neither matching the DSM/ortho CRS. The pipeline now
also emits `fused_utm.ply`, reprojected to the same UTM CRS as the orthomosaic.

## Bug Fixes

### fix(sfm): reconstruction used SIMPLE_RADIAL not OPENCV → lens distortion under-modelled → doming

**File:** `services/sfm/app/core/services/colmap_service.py`

**Root cause**

`extract_metadata` calls `pycolmap.import_images(camera_mode=AUTO)` without
specifying a camera model, so pycolmap creates the `cameras` rows with its default
**SIMPLE_RADIAL** model. `extract_features` runs afterwards and passes
`--ImageReader.camera_model OPENCV`, but because the cameras already exist COLMAP
reuses them and the OPENCV setting has no effect. Confirmed against a production
database: `cameras.bin` / the SQLite `cameras` table held `SIMPLE_RADIAL` with
`k1 = -0.469` (an implausibly large single coefficient), despite
`COLMAP_CAMERA_MODEL=OPENCV` in `.env`. SIMPLE_RADIAL has one radial term and no
`k2`/`p1`/`p2`, so it cannot fit the true lens distortion; the residual systematic
error is absorbed as a global curvature, doming the reconstruction. The domed DSM
in turn misaligns the multispectral bands, which are GPS-warped onto that surface.

**Fix**

- `import_images` now sets `camera_model` on a `pycolmap.ImageReaderOptions`
  so the database is created with the configured model (OPENCV) from the start.
  Implemented in `_import_images_with_model`, which sets the model defensively
  (`hasattr`-guarded — `single_camera` is **not** an `ImageReaderOptions` field
  in pycolmap 3.13, only `camera_model` is) and tries the known `import_images`
  call shapes (`options=` with/without `image_names`, legacy `image_list` /
  `reader_options`) before falling back to a plain import. Verified against
  pycolmap 3.13.0 in the container: the imported camera is now OPENCV (was
  SIMPLE_RADIAL).
- Added `_verify_camera_model`, which reads the model back from the COLMAP SQLite
  database after import and logs a clear warning on mismatch — so a silent
  regression surfaces at extract time, not as a bowl-shaped DSM days later.

### fix(sfm): testers could not extract coordinates — no UTM point cloud was produced

**File:** `services/sfm/app/core/services/colmap_service.py`

**Root cause**

The pipeline produced two clouds, neither usable for reading coordinates:
`fused.ply` is in arbitrary local SFM space (values near 0), and
`fused_georef.ply` is in **ECEF** (EPSG:4978) — geocentric XYZ in the millions of
metres, correct for the downstream PDAL reprojection but not human-readable and
not in the DSM/ortho CRS. Opening either in a viewer yields no meaningful
easting/northing, so coordinate extraction appeared broken even though the
georeferencing was correct (the ECEF centroid reprojects to the right lat/lon).

**Fix**

`mesh()` now also writes **`fused_utm.ply`**, reprojecting the ECEF cloud to the
same UTM CRS as the orthomosaic (`utm_epsg` from `geo_reference.json`) via the
same PDAL `filters.reprojection` the ortho pipeline already uses. The file is
recorded in `geo_reference.json` as `utm_pointcloud`, and a log line directs
testers to open it (not `fused.ply` / `fused_georef.ply`) for coordinates. The
step is non-fatal — a PDAL failure leaves the ECEF cloud in place.

## Known Limitations (documented, not yet addressed)

Recorded as docstring notes in the relevant functions after an architecture
review, so they are not rediscovered as bugs:

- **MS warp assumes nadir (ignores body roll/pitch).** `_warp_reflectance_image`
  places each band image at its GPS position and applies only *yaw*; body roll
  and pitch are not applied. On the DJI M3M the multispectral sensors are
  body-fixed (only RGB is gimballed), so the bands tilt with flight attitude — a
  ~10° roll at ~12 m AGL displaces the footprint centre ~2 m. Correct handling
  needs a collinearity/homography projection using `FlightRollDegree` +
  `FlightPitchDegree`. The recommended first step is to re-run with the
  camera-model doming fix and assess whether residual misalignment warrants it.
- **MS warp uses raw EXIF GPS, not the PPK/MRK-upgraded positions** that the SFM
  geo-registration uses — an accuracy gap specific to the MS-warp path.
- **DLS-only radiometric calibration, no Calibrated Reflectance Panel (CRP).**
  Absolute reflectance may carry a systematic offset; relative/index values are
  reliable. An Empirical Line Method / CRP path is not implemented.
