# v0.10.3 — Product Upload Resilience, Job Cancellation & Pipeline Concurrency Control

**Date:** 2026-03-29

Adds retry logic to all backend-facing HTTP calls in the product upload client, fixes job cancellation to propagate to active sub-services, and adds pipeline concurrency control to prevent multiple GPU-bound jobs from running simultaneously in HTTP dispatch mode.

---

## All Changes

### Bug Fixes

- `fix(upload)`: Add retry with linear backoff to all backend-facing calls in `ProductUploadClient` (`_initialize_upload`, `_get_chunk_url`, `_complete_upload`). Previously only S3 chunk uploads had retries — the init/chunk-url/complete calls to the Django backend failed immediately on `ConnectError` or `TimeoutException`. Now retries up to 5 times with `3s × attempt` delay.
- `fix(cancel)`: Propagate job cancellation to the active sub-service. The gateway cancel endpoint now reads the job's `current_stage` and forwards a cancel request to the corresponding sub-service client (`SFMClient.cancel_job()`, `OrthomosaicClient.cancel_job()`, `CalibrationClient.cancel_job()`). Previously, cancellation only killed the gateway's orchestrator asyncio task — sub-services continued running unaware.
- `fix(concurrency)`: Add pipeline-level concurrency control via `asyncio.Semaphore` to prevent multiple GPU-bound jobs from running simultaneously in HTTP dispatch mode (non-SQS). Previously, submitting multiple datasets concurrently would launch all pipelines in parallel, causing GPU OOM or data corruption. Now `run_pipeline_task` acquires a pipeline slot before starting and holds it until the entire pipeline completes via callback-driven signaling.

### Infrastructure

- `refactor(upload)`: Add `BACKEND_REQUEST_MAX_RETRIES` (default 5) and `BACKEND_REQUEST_RETRY_DELAY_SECONDS` (default 3.0) to `ProductUploadClientSettings`. Configurable via environment variables `BACKEND_BACKEND_MAX_RETRIES` and `BACKEND_BACKEND_RETRY_DELAY_SECONDS`.
- `refactor(cancel)`: Extract `_cancel_sub_services()` helper that maps `current_stage` → sub-service client and forwards cancel. Failures to reach sub-services are logged as warnings (non-blocking).
- `feat(concurrency)`: Add `max_concurrent_pipelines` setting to `BackgroundTaskSettings` (default 1, env var `BACKGROUND_TASK_MAX_CONCURRENT_PIPELINES`). Add `acquire_pipeline_slot()`, `signal_pipeline_complete()`, `release_pipeline_slot()`, and `wait_for_pipeline()` methods to `BackgroundTaskHandler`. Pipeline completion is signaled from callback processing (`process_callback_async`) on terminal paths (pipeline complete, stage failure, exception).

---

## Known Limitations / Future Work

- **COLMAP subprocess not killed on cancel:** The SFM service uses synchronous `subprocess.Popen` + `process.wait()` for COLMAP commands. When `asyncio.Task.cancel()` fires, `CancelledError` can only be raised at the next `await` point — so a COLMAP command already in progress will finish its current step before cancellation takes effect. The SFM service won't proceed to the next pipeline step, limiting wasted compute, but does not immediately free GPU/CPU resources. A future fix would convert to `asyncio.create_subprocess_exec()` or explicitly track and kill the subprocess PID on cancellation.
